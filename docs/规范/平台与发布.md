# 平台与发布

选型固定为桌面 Electron、Android Capacitor，共用 `web/` 的 React + Ant Design。平台范围由根目录 `client-platforms.json` 明确声明，遗留 Linux 打包配置不等于本轮发布 Linux。删除了本轮中止的 Flutter 工程，不重新设计组件主题。

当前目标为 macOS arm64/x64、Windows x64 与 Android arm64。要求支持不等于已有实现；Android 工程创建和前端资源复制只证明宿主接入，不能证明 VPN、持久化、订阅解析、后台任务、更新及开机行为已运行。移动后端必须接入 Android VpnService 和真实内核，不能调用不存在的 Electron IPC，不能用网页假数据通过功能验收。

Android 最低系统为 Android 8 / API 26，与无界面 JavaScriptEngine 的最低系统要求一致。系统 WebView 提供的沙箱能力还须在实际设备校验；已验证 Android 35 模拟器支持异步求值、安全数据传入、控制台消息和隔离实例终止。同一后台实例已接入共享业务服务，界面仅转发命令与事件。无界面专项测试覆盖真实配置读取、版本查询及前台脱离后的原生能力；不能据此宣称所有移动业务均已验收。

## 工具链

macOS Electron 开发及打包使用现有 Node、Go 和命令行工具，不安装完整 Xcode。Android 复用已有 JDK 21 与 Android SDK，由 `scripts/android-gradle.mjs` 定位，不将本机 SDK 路径提交入 Git。Windows 原生打包与安装验证在 Windows 环境运行；NSIS 使用引导式安装，可自行选择目录，不覆盖其他代理客户端。

## 更新边界

设置中的“检查更新”只检查软件和内核，不同步订阅、不测速、不检测网站。周期任务和配置变更初始化继续使用已有独立范围策略。应用和内核共用官方发布元数据读取器，API 失败时回退官方 Release 页面及资产摘要，不从第三方镜像获取可信摘要。

桌面后台维护在执行前持久化本轮触发时间，重新启动应用不会重置六小时周期；失败后的重新启动也不会立即重复请求供应商。无效记录及设备时钟回拨不能无限阻止维护，记录保存失败时不执行未登记的网络任务。下次唤醒按保存时间计算，停止服务后不重新武装时钟。配置引入和变更的局部初始化不受周期记录限制。Android 原生 WorkManager 使用唯一六小时任务唤醒同一后台宿主，网络可用时执行共享维护入口。专项测试覆盖任务去重与实例重建后读取持久化周期记录；尚未覆盖完整后台供应商更新流程，系统省电策略也不保证精确六小时执行。

签名更新目录优先使用发布者 Pages 渠道，固定 Ed25519 公钥、验证期限与资产身份；API 和官方 Release 页面作为独立读取备用渠道。客户端保存同一签名者已接受的最高发布时间与 payload 摘要；旧目录回放、相同发布时间的不同内容和保护记录保存失败均拒绝接受，不能绕过到备用渠道。桌面保护文件采用私有权限、原子替换并同步落盘，Android 保存在应用私有 SQLite。单次元数据读取期限独立于传输实现，底层忽略取消也不会永久阻塞检查。

下载从官方地址开始，失败后依次尝试候选镜像；预置包括 ghproxy.net 与 gh-proxy.org 服务系列，后者的 v4/cdn 是同一系列的不同端点，不能当作独立供应商或承诺永久可用。每次下载都验证同一官方 SHA-256，失败或取消删除临时文件，不能降级为只检查文件长度。平台及架构不支持时明确拒绝选择任意内核。自启设置须读取系统实际结果，不因写入调用返回就报告成功。

2026-10-11 公网专项从签名目录选择官方 SFA-version-metadata.json：官方地址及四个候选端点均 HTTP 200，54 字节内容通过同一可信 SHA-256。该验证证明当时的小资产通道可用，不代替各平台完整安装包下载、升级与重启验收。

签名 Android APK 的专用模拟器验证入口为 `npm run verify:android:release`，要求显式提供已有 SDK/JDK 与 `ANDROID_SERIAL=emulator-...`，默认保留测试应用数据库。报告记录实际签名、正式构建标识、同版本重装的数据保留、SQLite/JNI、真实 TUN 启停、无界面共享业务、后台任务去重与周期记录恢复、私有大配置启动，以及官方、ghproxy.net 和 gh-proxy.org 的同一可信小资产摘要。该专项报告明确排除版本升级、公开更新安装链路、原生布局、完整后台维护流程和开机恢复，不能代替完整平台发布证据。`--reset-fixture` 只适用于专用模拟器内的测试应用，不用于用户设备。

## 发布门禁

运行默认测试、真内核门禁、lint、前端类型与构建，再在对应原生系统检查启动、布局、代表性操作、真实代理请求、自启和更新。每个平台证据记录实际版本、提交及产物，不使用浏览器截图冒充系统验收。

`node scripts/check-client-platforms.mjs` 校验明确范围；发布前 `--release --evidence <path>` 要求版本和提交匹配、所有声明平台的原生检查通过及证据文件存在。它检查证据结构，不能替代实际测试。未完成的平台不发布占位安装包。

macOS 无 Developer ID/公证时必须如实标为未公证，不能称可无提示安装。Android 正式 APK 必须使用长期保留的发布签名，禁止用 debug 密钥冒充。密钥及用户配置位于仓库外。版本及安装包摘要与当前提交匹配后才创建公开 Release。

Android CI 使用 `SHADOW_ANDROID_KEYSTORE_BASE64`、`SHADOW_ANDROID_KEY_ALIAS`、`SHADOW_ANDROID_STORE_PASSWORD`、`SHADOW_ANDROID_KEY_PASSWORD` 四个私有发布 secret。密钥解码至 runner 临时目录，构建结束始终清理；仓库不保存密钥和密码。仅配置一个本机密钥路径不能让远程 runner 获得密钥。

发布 tag 必须与根包稳定版本一致，公开 tag 不强制覆盖。CI 汇总各平台真实测试生成的证据，缺报告、不同提交或引用不存在的文件均失败；不会根据安装包存在自行生成“通过”。安装包文件构建完成不等于全功能验收完成。

## 安装后的原生验收入口

`verify-desktop-installed.mjs --exe <已安装程序>` 在独立验收配置目录启动真实安装包，通过公开业务 IPC 验证软件/内核版本、平台与架构、构建提交、配置写回和系统自启注册读回。结束时恢复原自启状态并关闭本次进程。报告记录实际可执行文件与应用归档摘要；布局、真实代理、登录后自启及更新安装不由该专项推断。Windows CI 通过 `verify-windows-install.ps1` 将 NSIS 安装到带空格的自选目录，确认真实可执行文件后运行该专项。CI 尚未执行时不得写成 Windows 已验证。

Android `verify-android-release.mjs --baseline-apk <旧签名包>` 可验证真正的版本升级：先检查包身份、长期签名一致以及旧 versionCode 严格小于新包，再在旧包写入专用数据库标识，安装新包后确认新版本和标识保留。未提供旧包仍只是同版本覆盖安装；公开更新下载和安装器行为须另验，不能从 ADB 安装结果推断。

## 更新请求的自动网络路径

应用、内核和分流资源更新以及图标请求只根据本应用拥有的代理运行态与有效入口端口选择会话；未运行或入口不可用时使用独立直连会话，不读取配置来决定每个请求。已退役的 mainSessionViaProxy 从类型、默认值、持久化校验、运行分支和兼容内核生成器删除，存量及恢复导入统一在配置边界清理。订阅同步仍按其统一获取策略尝试直连和代理，不增加手动路径开关。

正式 tag 前可手动运行 Release 工作流生成候选：同源 macOS 双架构 DMG、Windows 安装包、长期签名 APK，以及两种 macOS 架构的实际 DMG 安装与业务验收。候选只上传内部产物，不创建软件 Release；公开发布仍要求匹配版本的不可变签名 tag 和完整原生证据门禁。候选版本检查只接受 workflow_dispatch 分支构建，不能用于 push/tag 发布绕过版本核对。
