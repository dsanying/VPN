# 多内核兼容

2026-10-08：以官方稳定版本为基线，sing-box 1.14.2 / Xray-core 26.3.27 / mihomo 1.19.32。Xray 最新预发布版本不混入稳定通道；两辅助内核下载归档与二进制摘要均固定，并在启动前验证二进制。

## 执行关系

| 数据 / 节点 | 执行路径 |
| --- | --- |
| 原有 sing-box 可执行协议 | sing-box |
| VLESS / VMess / Trojan 的 XHTTP、SplitHTTP | sing-box → Xray → sing-box 明确直连入口 → 节点 |
| 原生 Xray JSON 中支持映射的 VLESS / VMess / Trojan / Shadowsocks | 完整保留原生 outbound，由 Xray 检查与执行 |
| Clash SSR、Hysteria v1、Mieru、Sudoku、ShadowQUIC、TrustTunnel、MASQUE | 完整保留 native proxy，由 mihomo 检查与执行 |
| SSR 明文 / Base64 分享订阅 | 解析为 mihomo native proxy |

Xray / mihomo 只运行节点出站；不另外接管系统路由、安装后台服务或加载供应商的路由、监听器、远程 provider。sing-box 统一接管、分流、DNS、连接统计。桥接仅监听 127.0.0.1，使用随机 SOCKS 凭据。辅助内核的上游拨号回到 sing-box 明确的直连入口，避免自身拨号在 TUN 下再次进入同一代理。显式前置代理链使用专用回拨入口，保留所选前置节点；循环或缺失目标明确失败。

测速采用同一能力选择：运行中走主核独立探测槽，断开时启动隔离的临时核及必要辅助核。TCP 建连只表示入口延迟；代理延迟仍须经节点完成请求。没有因接入新内核而关闭 TLS 校验。

两条测速流程固定且独立于用户分流规则：入口延迟测本机经物理接口到节点的实际连接；代理延迟通过专用测速入站强制走指定被测节点，再完成目标请求。管理 API 仅负责选择测速槽，API 成功不作为代理可用证据。智能、全部代理、直连，以及应用或域名规则均不得改变测速指定的路径。入口无法证明直连、节点参数已修改未生效或内核中途停止时，不以其他路径的结果补写成功值。

系统接管与应用规则另行验收：真实应用请求及内核连接记录用于确认进程、命中规则和实际出站，不取代上述两条测速，也不使节点测速跟随规则。`scripts/verify-tun-route.cjs` 是针对普通 Node 进程 OS socket 的独立 TUN 验证工具；请求成功但未观察到对应连接、出站或进程不符合预期均不会通过。它不验证 Firefox，也不读取系统代理设置代替真实应用验证。

## 字段与更新

XHTTP 保留 host / path / mode / extra / xmux / downloadSettings 等原生扩展；分离下载链路同样固定回拨。分享链接支持 xhttp / splithttp 别名。原生 Xray JSON 不以简化字段替代原始 outbound，因此 KCP 等额外传输参数可以提交给实际 Xray 内核验证，不静默变成 TCP。

SSR 保留 cipher / password / protocol / obfs / protocol-param / obfs-param 等；分享链接可往返保存中文备注与扩展字符串。无法在 SSR 分享链接中表达的 native 布尔 / 对象字段明确拒绝分享并提示导出原生配置，避免丢字段。

未知协议、无效参数或引用本地证书私钥文件的远程订阅给出明确失败；不将供应商指定的外部路径或其他出站引用直接交给内核。一个配置无效的辅助节点不会阻止其他合法节点通过内核校验。更新沿用原条件请求和失败保留机制；改名或调整传输参数不改变稳定节点身份。

## 已验证与边界

- macOS arm64：官方真核验证 XHTTP auto / packet-up / stream-up 完整 HTTP 请求，经 sing-box → Xray → sing-box 直连入口到本地协议服务器；停止辅助核后请求失败，不回落直连。
- macOS arm64：mihomo native 节点完整代理请求、SOCKS 随机认证、单个错误节点隔离；SSR、XHTTP 扩展配置通过各自官方核心检查。
- 四个平台的辅助内核归档与二进制 SHA-256 均校验；Windows x64、Linux x64、macOS x64 尚未执行原生运行验证。
- 不等同于所有协议、插件、传输组合均已端到端验证：SSR 执行配置已检查，暂无本地 SSR 服务端握手验证；Hysteria v1 / Mieru 等列出的 native 配置转交路径已接入，但需各协议服务端分别验证。XHTTP stream-one 需要相应 TLS / HTTP2 条件，未用无 TLS 的本地 HTTP 夹具冒充覆盖。
- 不因导入成功而保证供应商节点在线。真实节点超时、握手拒绝和地区限制仍需依据实际请求结果。

接口代码：CompatibilityCoreService.ts 管理进程生命周期与完整性；compatibility-config.ts 生成桥接配置；core-capabilities.ts 提供唯一的能力选择。内核版本、许可证及安全脱敏记录纳入诊断报告。

## 本机真实订阅结果

官方订阅重新同步后，此前因 XHTTP 被拒绝的“韩国”VLESS 节点已导入。客户端实际代理检测结果为首端点 TLS 连接重置、备用端点超时；独立官方 Xray（不经过客户端桥接）对 Google 与 Cloudflare 检测端点同样出现 HTTPS 握手超时。因此已排除“只是不认识 XHTTP”的导入问题，尚不能确认该供应商节点可用，也不能仅凭这些结果把原因锁定为供应商服务器。

统计沿用 sing-box 的原始口径：辅助内核回拨连接也属于内核接管的连接，其流量及协议开销会进入总量；当前没有把该总量称为去重后的纯应用净流量。TUN 防回环机制有配置和完整回拨请求验证，本轮未通过修改用户的系统路由进行真实 TUN 启停实测。
